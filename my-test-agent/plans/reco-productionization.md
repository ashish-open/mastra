# Blueprint — Productionize OpenArc Reconciliation (Two-Workflow Split + Hardening)

> Generated by `/blueprint`. Each step is self-contained: a fresh agent can execute it cold.
> **Cross-repo:** steps tagged `[mastra]` live in `my-test-agent/`; `[openarc]` in `openarc-dashboard/`.
> Branch base: `meeting-and-support-agents`. Use one PR per step.

## Objective

Split the single `reconcileWorkflow` into two workflows that share primitives, make the OpenArc
run-detail UI workflow-type-aware, and productionize the deterministic YES settlement recon.

## Core principle (why split)

Settlement is **audit-critical money work** — deterministic, no LLM in the decision path
(Principle 1). The LLM surfaces (fuzzy match, disposition agent, suspend/resume review gate,
decisions table, Approve/Reject) are dead weight *and confusing* for settlement, but valuable for
lower-stakes recon. Two workflows = clean separation; shared `matcher / adapters / db /
report-pack / disposition-engine` = no duplication.

## Decisions locked

| Question | Decision |
|---|---|
| Remove decisions table? | Not globally — make UI **workflow-type-aware**. Deterministic → summary + reports. LLM → decisions + review. |
| Two workflows? | **Yes.** `settlementReconWorkflow` (deterministic) + `llmReconWorkflow` (LLM). |
| Share code? | Yes — only the workflow step-graph differs; primitives are shared modules. |
| Workflow IDs in OpenArc | Discover via `/integration/info` (never hardcode). Keep `reconcile-workflow` id stable for back-compat where possible. |

## Dependency graph

```
S1 (extract shared steps) ──┬─► S2 (deterministic wf) ─┐
                            └─► S3 (llm wf) ───────────┴─► S4 (UI type-aware) [openarc]
S5 (open_prod read-only)  ── independent
S6 (Postgres persistence) ── independent of S1-S4, coordinate infra
S7 (scheduling + alerts)  ── after S2
S8 (observability/deploy) ── after S2,S6
S9,S10 (scale-out)        ── future, after S1-S8
```
Parallel: **S2∥S3** (after S1); **S5∥S6** anytime; S4 after S2+S3.

## S1 — Extract shared workflow step factories  `[mastra]`  · model: strongest

**Context brief.** `src/mastra/reconciliation/workflow.ts` is one `reconcileWorkflow` with an
`llm:'off'` branch inside `deterministicMatchStep`, plus fuzzy/disposition/review-gate steps. To
support two workflows we first refactor steps into reusable, independently-testable units with NO
behavior change.

**Tasks.**
- Add `workflowType: 'deterministic' | 'llm'` to `ReconcileConfig` (or derive from `llm`). Default `'llm'` for back-compat; settlement configs = `'deterministic'`.
- Extract step builders into `workflow-steps.ts`: `openRunStep`, `fetchAllSourcesStep`, `deterministicMatchAndDisposeStep` (legs + auto-refund lookup + disposition + persist summaries + markComplete-flag), `buildReportPackStep`. Keep `fuzzyMatchStep`, `dispositionStep`, `reviewGateStep`, `writeDecisionsStep` as the LLM-only set.
- No new workflow yet. `reconcileWorkflow` keeps working by composing the extracted steps.

**Verify.** `npx tsc --noEmit -p .`; run an existing run end-to-end → byte-identical reports vs pre-refactor (snapshot the 3 CSVs before/after).
**Exit.** Steps are standalone factories; existing workflow unchanged in behavior.

## S2 — `settlementReconWorkflow` (deterministic)  `[mastra]`  · model: default

**Context brief.** Settlement needs NO LLM steps. Build a lean workflow from S1 factories.

**Tasks.**
- New `createWorkflow({ id: 'settlement-recon' })`: `openRun → fetchAllSources → deterministicMatchAndDispose → buildReportPack`. No fuzzy/disposition-agent/review-gate.
- Register in `index.ts`. Point `settlement-yes-pg` (and future settlement configs) at it.
- Persist only per-MIS disposition summaries (already the behavior). Purge staging post-run (env-gated).

**Verify.** Trigger settlement-yes-pg → 3 reports + summary correct; no suspend; snapshot matches S1 baseline.
**Exit.** Deterministic settlement runs on its own workflow id, zero LLM steps.

---

## S3 — `llmReconWorkflow` (LLM)  `[mastra]`  · model: default · ∥ S2

**Context brief.** The existing fuzzy + disposition-agent + review path for lower-stakes recon.

**Tasks.**
- New/renamed `createWorkflow({ id: 'llm-recon' })` (or keep `reconcile-workflow` id here for back-compat): `openRun → fetchAllSources → deterministicMatch(no dispose) → fuzzy → disposition → reviewGate → writeDecisions`. Drop the inline `llm:'off'` branch (this wf is always LLM).
- Non-settlement configs (bank-pg-internal, restaurant-swiggy, etc.) route here.

**Verify.** `pnpm eval:reco` accuracy unchanged; a bank-pg-internal run still suspends/resumes.
**Exit.** LLM configs run on the LLM workflow; settlement configs do not touch it.

## S4 — Workflow-type-aware run-detail UI  `[openarc]`  · model: default · after S2,S3

**Context brief.** `ReconcileRunDetail.tsx` currently always renders the decisions table. Make it
branch on workflow type. OpenArc must learn workflow ids from `/integration/info` (never hardcode).

**Tasks.**
- Backend: extend run metadata / `/integration/info` consumption so OpenArc knows a run's `workflowType`.
- Deterministic run → render `SettlementSummaryCard` + `ReportPackCard` only; **drop the decisions table**.
- LLM run → keep decisions table + review banner + Approve/Reject (already gated on `state==='suspended'`).
- Update `RECO_WORKFLOW_ID` usage → discover both ids dynamically.

**Verify.** Settlement run page = summary + reports, no decisions; LLM run page = decisions + review.
**Exit.** UI surface matches workflow type; no stray Approve/Reject on settlement.

## S5 — Connect read-only `open_prod` for auto-refunds  `[mastra/infra]`  · model: default · independent

**Context brief.** `yes-auto-refunds` adapter is coded + env-gated on `RECO_OPEN_PROD_URL`. Needs a
real read-only DSN + validation.

**Tasks.**
- Provision a **read-only** open_prod Postgres credential; set `RECO_OPEN_PROD_URL` in prod env (never commit).
- Run YES settlement with DSN set; confirm the ~27 "Checking" split into Auto Refund Success/FAILED/Pending.
- **Validate counts against the finance Metabase query** for the same day before trusting.

**Verify.** `[yes-auto-refunds] looked up N → M` logs; summary Auto-Refund lines match Metabase.
**Exit.** Auto-refund categories live and validated; FAILED refunds surface in exception report.

## S6 — Migrate reco persistence LibSQL/SQLite → Postgres  `[mastra]`  · model: strongest · independent

**Context brief.** `reco.db` (LibSQL) holds runs/decisions/staging. Single-writer + the duckdb-lock
gotcha make it unfit for prod. Move to Postgres (OpenArc's, or a dedicated reco schema).

**Tasks.**
- Port `db.ts` schema + queries to Postgres (`pg`). Keep the same table shapes + idempotency keys.
- Batched multi-row inserts for decisions/staging (the 145k row-by-row insert was a bottleneck).
- Retention policy: 18 months online, archive beyond (plan §scale).
- Keep adapter contract stable; only the storage backend changes.

**Verify.** Full settlement run persists + reads from Postgres; report pack identical; load test 50k rows < 5 min.
**Exit.** No SQLite in the prod reco path; no single-writer lock.

## S7 — Daily scheduling + missing-file alerting  `[mastra]`  · model: default · after S2

**Context brief.** `expected_resolution_days` exists on `ReconcileConfig`. Add expected-file SLAs +
a scheduled trigger.

**Tasks.**
- Add `expectedFiles: { adapterId, dueBy }[]` to settlement config.
- Cron (per PG): at SLA time, check which expected sources are staged for today; Slack/dashboard alert on gaps.
- Auto-trigger the settlement run when all files present (or on a fixed schedule).

**Verify.** Withhold one file → alert fires listing the missing slot; all present → run auto-starts.
**Exit.** Hands-off daily operation with gap alerts.

## S8 — Observability + deploy hardening  `[mastra/infra]`  · model: default · after S2,S6

**Tasks.**
- Structured logs already present (`[reco] …`); ship to a log sink. Mastra traces enabled in prod.

**Verify.** Induce a failing run → alert + trace captured; restart leaves no orphaned lock.
**Exit.** Operable in prod with visibility + safe restarts.

## Adversarial review notes (Phase 4)

- **Back-compat risk:** OpenArc hardcodes `RECO_WORKFLOW_ID='reconcile-workflow'`. S3/S4 MUST migrate OpenArc to discover ids via `/integration/info` or the split breaks the dashboard. Mitigation: keep one id stable, add the second via discovery.
- **No primitive duplication:** S2/S3 must import the SAME matcher/adapters/db/report-pack — only the `createWorkflow` graph differs. Reviewer checks for copy-paste.
- **Determinism gate:** S1 refactor must produce byte-identical reports (snapshot test) — non-negotiable for money work.
- **PII:** S5 read-only credential only; S6 Postgres must honor the post-run staging purge.
- **Sequencing:** ship S1→S2→S4 first (the user's immediate ask + clean UI). S5 can land in parallel. S6 is the heaviest; do after the split is stable.
